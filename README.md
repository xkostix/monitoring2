### Задание 1

Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы выведите в мониторинг и почему?

### Решение

1) CPU-метрики (вычисления), поскольку вычисления загружают CPU. Точнее:
* CPU utilization (%) по ядрам/подам/хостам. Нужны конкретные показатели, такие как user, system, iowait, irq.
* Load Average (1m, 5m, 15m) — показывает, есть ли очередь потоков на выполнение задач.
* CPU throttling в основном для контейнеров, не режутся ли вычисления лимитами.

2) Метрики диска, поскольку отчеты сохраняются на диск.
* Свободное место на диске - при его отсутствии отчеты не будут сохраняться.
* Disk I/O (очередь к диску, IOPS) - чтобы запись не стала узким местом в процессе.
* Inode usage — бывает проблема при большом количестве мелких файлов.

3) HTTP-метрики (доступность и производительность), поскольку взаимодействие с платформой по HTTP.
* HTTP-коды ответов (2xx / 4xx / 5xx) — критично для понимания, отвечает ли сервис успешно.
* Доля успешных запросов к общему числу запросов.
* RPS (requests per second) по эндпоинтам — показывает текущую нагрузку на платформу.
* Количество активных соединений — полезно для понимания, не упирается ли сервис в лимиты.

4) Метрики вычислений и отчётов (бизнес-логика). HTTP может быть 200 OK, а вычисление — падать или отчёт не записываться. Эти метрики отражают реальную SLI платформы.
* Количество запущенных / завершённых / упавших вычислений (success/failure rate).
* Latency (p50, p95, p99) времени ответа — средняя задержка может скрывать проблемы; перцентили покажут, как чувствуют себя в т.ч. отдельные запросы или хвосты запросов.
* Ошибки записи на диск (I/O errors, permission denied, disk full) — критично, т.к. отчёты сохраняются на диск.

5) Также полезны метрики такие как:
* Memory usage — вычисления могут потреблять много RAM, утечки приведут к OOM.
* Network I/O — чтобы сеть не стала узким местом.

### Задание 2

Менеджер продукта посмотрев на ваши метрики сказал, что ему непонятно что такое RAM/inodes/CPUla. Также он сказал, что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы можете ему предложить?

### Решение

Менеджер хочет знать текущие SLI, и укладываемся мы в SLA. Можно предложить метрики похожие на п. 3 и 4 из предыдущего задания. Мы можем ему предложить метрики и графики:
1. Доля успешных HTTP-запросов: availability = успешные_запросы / все_запросы. И доля неуспешных запроаов. Для менеджера это будет означать "насколько часто клиент не может получить ответ от сервиса".
2. Успешность вычислений: доля вычислений, завершившихся успешно или неуспешно. Для менеджера это "насколько часто клиент получает результат, без ошибок".
3. Скорость ответа (Latency), не среднее, а перцентили. Время ответа на запрос на p95 и p99. "Насколько быстро клиент получает ответ".
4. Доля отчётов, успешно записанных на диск и доступных для чтения. report_availability = успешно_записанные_отчёты / все_отчёты. То есть "может ли клиент получить свой отчёт после вычисления".
5. Время вычисления отчета. "Сколько ждёт клиент, пока считается отчёт".

Также можно перевести на понятный язык RAM/inodes/CPUla. То есть: не падает ли сервис от нехватки памяти, не пора ли удалить или заархивировать старые файлы, справляемся ли с нагрузкой.

### Задание 3

Вашей DevOps команде в этом году не выделили финансирование на построение системы сбора логов. Разработчики в свою очередь хотят видеть все ошибки, которые выдают их приложения. Какое решение вы можете предпринять в этой ситуации, чтобы разработчики получали ошибки приложения?

### Решение

Надо выяснить у разработчиков, какие именно ошибки они хотят видеть, какой уровень ошибок. Как получать или искать, как хранить и т.д. Далее такие варианты:
1. Самый простой: приложения логируются в systemd journal, разработчики смотрят journalctl -u myapp -p err.
2. Файлы логов + grep + Slack-бот. Приложения пишут ошибки в отдельный файл errors.log. Скрипт раз в минуту грепает новые ошибки и шлёт в Slack/Telegram.
3. Находим или выделяем сервер. Все приложения шлют логи (ошибки) по syslog на один сервер, там они пишутся в файлы. На сервере — rsyslog, принимает по TCP/UDP. Файлы ротируются через logrotate.
4. Приложения пишут логи в файлы на общем NFS/SMB, разработчики подключаются и смотрят.
5. Развернуть Sentry self-hosted (free tier). Подключить SDK в приложениях. Разработчики видят ошибки в UI с группировкой, стектрейсами, контекстом.
6. GlitchTip (open-source альтернатива Sentry). Бесплатно, нужно меньше ресурсов, чем Sentry.
7. Grafana Loki (self-hosted, single binary). Развернуть Loki в single-binary режиме. Promtail собирает логи с серверов. Grafana UI для поиска.
8. Vector + файлы + Grafana. Легковесно.
9. Бесплатные free tier тарифы облачных лог-систем. Но есть лимиты, может стать платным, данные у третьих лиц.

### Задание 4

Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?

### Решение

Помимо 2хх ответов есть другие успешные ответы - 3хх, их надо учесть в числителе. Например, значительная часть ответов - это 304 Not Modified для кеширующих клиентов. А считать за summ_all_requests не следует такие ответы как 4xx — это вина клиента, их не считаем в SLA (или считаем отдельно). Также не следует в знаменателе считать прочие ответы, отличающиеся от 2xx, 3xx, 5xx. В итоге лучше считать так:

SLA = sum(2xx + 3xx) / sum(2xx + 3xx + 5xx)

### Задание 4

Опишите основные плюсы и минусы pull и push систем мониторинга.

### Решение

Pull:

Плюсы:
* Централизованный контроль подлинности — сервер знает, кого и когда опрашивать.
* Легко обнаружить «мёртвый» target (scrape fail = сервис недоступен).
* Конфигурация targets в одном месте.
* Нет нагрузки на сервис, если мониторинг не опрашивает.
* Проще отладка — можно вручную дёрнуть /metrics.

Минусы:
* Плохо работает с короткоживущими job'ами - не успеет опросить.
* Проблемы с таргетами за NAT/firewall — сервер мониторинга должен достучаться до target, надо настраивать на каждом таргете.
* Service discovery обязателен при динамике (Kubernetes).

Push:

Плюсы:
* упрощение репликации данных в разные системы мониторинга или их резервные копии.
* более гибкая настройка отправки пакетов данных с метриками.
* UDP — это менее затратный способ передачи данных, из-за чего может возрасти 
производительность сбора метрик
* Работает с короткоживущими job'ами (batch, cron, Lambda).
* Не требует доступа извне к сервису — идеально для клиентов за NAT, firewall.
* Метрика появляется сразу (real-time) в момент возникновения события.

Минусы:
* Сложно понять, жив ли сервис — если метрики не приходят, это может быть и падение, и отсутствие нагрузки.
* Нет централизованного контроля — каждый клиент должен знать, куда пушить.
* Риск потери метрик при недоступности коллектора (нужна буферизация на клиенте).
* Можно завалить коллектор (нужен rate limiting, aggregation).
* Сложнее отладка — не видно, что именно отправил клиент, виден только результат доставки.
* Дублирование конфигурации на каждом клиенте.

### Задание 5

Какие из ниже перечисленных систем относятся к push модели, а какие к pull? А может есть гибридные?
Prometheus
TICK
Zabbix
VictoriaMetrics
Nagios

### Решение

Push-модели:
* TICK

Pull-модели:
* Prometheus, но с поддержкой Push через шлюз - для короткоживущих задач (batch-джобов, cron) предусмотрен Pushgateway.

Гибридные:
* Zabbix: Pull по умолчанию + Push как опция.
* VictoriaMetrics: Pull + Push
* Nagios: Pull по умолчанию + Push как опция
